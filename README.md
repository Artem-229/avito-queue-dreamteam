# Авито Очередь

MVP сервиса пользовательской очереди на дефицитные товары. Пользователь встаёт
в очередь перед чекаутом и получает временное персональное право на покупку —
система гарантирует, что одна единица товара не уйдёт двум покупателям.

**Команда 33 «Dream Team»** · Avito Start, кейс 2

## Стек

- **Backend:** Go 1.25, gin, pgx/v5, viper
- **Frontend:** React 18 + TypeScript + Vite (feature-sliced), TanStack Query, zustand
- **База данных:** PostgreSQL 17 + pgvector — единственное хранилище
- **Миграции:** goose, отдельным контейнером `migrator`
- **ИИ:** GigaChat Embeddings → векторный подбор похожих лотов (см. «ИИ в продукте»)
- **Запуск:** Docker Compose

## Структура проекта

```
/cmd                            — точка входа
/internal
  /app                          — сборка зависимостей, старт/остановка
  /config                       — configs/configuration.yaml через viper + env-переменные
  /domain                       — доменные типы и сентинел-ошибки, без внешних зависимостей
  /clients/gigachat             — клиент эмбеддингов + файловый кэш векторов
  /infra/http/rest              — gin: server.go, router.go, handlers/, middlewares/, session/
  /infra/postgres/repository    — репозитории (pgx), транзакции, db(ctx, pool)
  /services                     — CatalogService, QueueEntryService (Reconcile/Buy),
                                  ChanceCalculator, DemoService, StatsService
                                  + интеграционные тесты
/migrations                     — goose, нумерация 00001, 00002, ...
/docs                           — REQUIREMENTS.md и производные
/frontend                       — React + TypeScript + Vite, feature-sliced
```

Правило зависимостей: `repository → services → handlers`, `domain` ни от чего не зависит.
Интерфейсы репозиториев объявлены на стороне потребителя (в `services`). Хендлеры
обращаются только к сервисам, никогда к репозиториям напрямую.

## Быстрый старт

**Демо:** http://111.88.149.139:3000

Требования: Docker и Docker Compose. Больше ничего ставить не нужно.

```
docker compose up -d --build
```

Поднимаются четыре сервиса: `postgres`, `migrator` (накатывает миграции и
завершается), `app` и `frontend`. Приложение доступно на
<http://localhost:3000>, API — на <http://localhost:8080>.

Проверка:

```
curl http://localhost:8080/health
```

Так поднимается **весь основной сценарий кейса**: очередь, право на покупку,
таймер, покупка, `sold_out`, шанс на покупку, симулятор, метрики и админка с
ключом по умолчанию. Одна функция при этом работает вхолостую — подбор похожих
лотов, потому что он опирается на векторы, а их считает GigaChat.

### Ключи (что включают и что ломается без них)

Секреты берутся из файла **`.env` рядом с `docker-compose.yaml`**; ни один из них
не закоммичен. Шаблон — `.env.example`, скопируйте его и подставьте свои значения:

```
cp .env.example .env
```

| Переменная | Без неё | С ней |
|---|---|---|
| `GIGACHAT_AUTH_KEY` | прогрев векторов падает с `401`, `GET /catalog/:id/similar` отвечает `500`, блок «похожие лоты» и `alternatives` пустые | семантический подбор альтернатив работает во всех состояниях |
| `ADMIN_SECRET_KEY` | админка отвечает `503 ADMIN_DISABLED` | вход в `/admin` по этому ключу |
| `AUTH_SESSION_SECRET` | в compose подставляется дев-значение; на публичном стенде задайте своё | подпись сессий |

После добавления ключа GigaChat нужен перезапуск приложения — векторы считаются
на старте:

```
docker compose up -d --force-recreate app
docker compose logs app | grep GIGACHAT
```

В логе должны идти строки `[GIGACHAT API CALL]` без `401`. Проверка результата —
`GET /api/v1/catalog/<id>/similar` возвращает непустой список.

> Если база уже содержит товары с векторами, прогрев их не трогает: он заполняет
> только те, у которых `embedding IS NULL`. Чтобы пересчитать всё с нуля —
> `docker compose down -v && docker compose up -d --build`.

### Запуск бэкенда с хоста

Наружу Postgres проброшен на порт **5433** (только на `127.0.0.1`), а `configs/configuration.yaml`
рассчитан на адрес внутри docker-сети, поэтому адрес переопределяется
переменными окружения:

```
docker compose up -d postgres migrator
DB_HOST=localhost DB_PORT=5433 AUTH_SESSION_SECRET=local-development-session-secret-change-me go run ./cmd
```

### Запуск фронтенда в dev-режиме

Нужен для разработки и для текстовой ИИ-рекомендации на экране «товар
закончился» — она реализована плагином dev-сервера Vite и в Docker-сборке не
существует (подробнее — «ИИ в продукте»):

```
docker compose up -d postgres migrator app   # бэкенд на :8080
cd frontend
cp .env.example .env.local                   # и вписать GIGACHAT_AUTH_KEY
npm ci
npm run dev                                  # http://localhost:5173
```

Открывать нужно **:5173**, а не :3000: dev-сервер сам проксирует `/api` на
`localhost:8080` и сам обслуживает `/ai/recommendation`.

### Тесты

Тесты доменной логики интеграционные — они проверяют реальные блокировки строк
и реальный констрейнт, а не поведение моков. Без поднятой базы они скипаются, а
не падают, поэтому в выводе стоит смотреть не только на `ok`, но и на `SKIP`:

```
docker compose up -d postgres migrator
go test -race -count=1 ./internal/...
```

Адрес базы по умолчанию — тот, что пробрасывает compose (`localhost:5433`),
поэтому переменная нужна, только если база живёт где-то ещё:

```
TEST_DATABASE_DSN="postgres://postgres:postgres@<host>:<port>/avito_queue?sslmode=disable" \
  go test -race -count=1 ./internal/...
```

Фронтенд:

```
cd frontend && npm ci && npm run lint && npm run typecheck && npm run test
```

> Путь `./internal/...`, а не `./...`: последний заходит в `frontend/node_modules`,
> где лежит чужой Go-код.

> Если база была поднята до последних изменений схемы, goose не перенакатит уже
> применённые миграции — нужно один раз пересоздать том: `docker compose down -v`.

> Тест прогрева векторов (`TestWarmupEmbeddings_FillsMissingVectors`) вызывает
> `WarmupEmbeddings`, а тот идёт по всей базе и проставляет тестовые векторы всем
> товарам без эмбеддинга. После прогона тестов на демо-базе подбор похожих лотов
> будет выдавать случайный порядок — лечится тем же `docker compose down -v`.
> Гонять тесты против стенда не нужно, для них поднимается отдельная база.

## Конфигурация

| Переменная | Обязательна | По умолчанию | Назначение |
|---|---|---|---|
| `AUTH_SESSION_SECRET` | **да** | в compose — дев-значение | Ключ HMAC для подписи сессии, минимум 32 байта. Приложение не стартует без него |
| `AUTH_SECURE_COOKIE` | нет | `false` | Флаг `Secure` на куке сессии. На HTTPS-стенде обязателен |
| `ADMIN_SECRET_KEY` | нет | в compose — `admin-local-dev-key` | Ключ админ-панели. Пустой ключ = админка отвечает `503`, остальной сервис работает штатно |
| `GIGACHAT_AUTH_KEY` | нет | — | Доступ к GigaChat Embeddings. Без него нет векторов, а значит нет похожих лотов |
| `DEMO_ENABLED` | нет | `true` (`configs/configuration.yaml`) | Включает демо-ручки `/demo/simulate` и `/demo/expire-now` |
| `DB_HOST`, `DB_PORT`, `DB_USER`, `DB_PASSWORD`, `DB_NAME` | нет | из `configs/configuration.yaml` | Подключение к Postgres |

Секретов в конфиг-файле нет намеренно: закоммиченный секрет известен всем, у кого
есть доступ к репозиторию, а подпись на публично известном ключе не защищает ни
от чего. Поэтому `AUTH_SESSION_SECRET`, `ADMIN_SECRET_KEY` и `GIGACHAT_AUTH_KEY`
живут только в переменных окружения.

Отсутствие ключей влияет на систему по-разному, и это тоже осознанное решение:
без секрета подписи приложение **не стартует** (сервис без защиты личности хуже,
чем упавший сервис), а без админского ключа и ключа GigaChat — стартует и
работает, просто с выключенными второстепенными функциями.

## API

Все ручки под `/api/v1`. Сессия не требуется только для `/demo/login`,
`/admin/login` и `/health`; админские ручки требуют сессию **и** заголовок
`X-Admin-Key`.

### Авторизация

Настоящей регистрации в MVP нет, но право на покупку обязано к кому-то
крепиться. `POST /demo/login` выдаёт случайный `user_id`, подписанный
HMAC-SHA256 вместе со сроком жизни.

```
POST /api/v1/demo/login      {"display_name": "Аня"}
  → 200 {"user_id": "...", "display_name": "Аня", "token": "<user_id>.<exp>.<sig>"}
    + Set-Cookie: session=<token>; HttpOnly; SameSite=Lax
```

Токен принимается двумя способами и проверяется одинаково:

- заголовком `Authorization: Bearer <token>` — так работает переключатель
  тестовых аккаунтов: кука `httpOnly`, JS её не читает, поэтому больше одной
  сессии в браузере через куку не удержать;
- кукой `session` — обычный вход.

Заголовок имеет приоритет над кукой: явно выбранный аккаунт должен побеждать.
Неподписанной идентификации не существует — назвать себя чужим `user_id`
нельзя, это и есть механизм непередаваемости права (RGT-05).

### Каталог и очередь

| Метод | Путь | Описание |
|---|---|---|
| `GET` | `/catalog` | Список товаров |
| `GET` | `/catalog/:id` | Карточка товара: плюс `queue_size` и `chance_if_join` — шанс купить, если встать в очередь сейчас (`null` у распроданного) |
| `GET` | `/catalog/:id/similar` | Похожие лоты по векторной близости, только с остатком — распроданное взамен распроданного не предлагается. Требует `GIGACHAT_AUTH_KEY` |
| `POST` | `/catalog/:id/queue` | Встать в очередь. Идемпотентно: повторный вызов возвращает текущее состояние, а не ошибку |
| `GET` | `/catalog/:id/queue/me` | Состояние участия. Эту ручку поллит фронт, она же продвигает очередь |
| `DELETE` | `/catalog/:id/queue/me` | Покинуть очередь |
| `POST` | `/catalog/:id/purchase` | Потратить выданное право (заглушка оплаты) |
| `GET` | `/stats` | Метрики: длина очередей по товарам, конверсия права в покупку, среднее ожидание |

Все три ручки очереди возвращают один и тот же конверт состояния. Пример для
ожидающего:

```json
{
  "status": "waiting",
  "message": "Вы в очереди. Пожалуйста, подождите освобождения слота.",
  "position": 7,
  "initial_position": 12,
  "progress_percent": 45,
  "queue_size": 23,
  "chance": { "percent": 61, "basis": "item" },
  "expires_at": null,
  "server_time": "2026-08-10T03:07:49+03:00",
  "eta_seconds": null,
  "next_step": { "kind": "wait", "label": "Ожидайте, статус обновится сам" },
  "alternatives": []
}
```

`status` принимает значения `not_in_queue`, `waiting`, `granted`, `purchased`,
`expired`, `sold_out`, `cancelled`. У каждого есть `message` и `next_step` —
серых зон без объяснения происходящего в API нет.

Поля, зависящие от состояния:

- `chance`, `position`, `initial_position`, `progress_percent` — только у
  `waiting`. `basis` говорит, на чём посчитан шанс: `item` (конверсия этого
  товара), `global` (общая по системе), `default` (данных ещё нет);
- `expires_at` — только у `granted`, это дедлайн оплаты;
- `alternatives` (id похожих нераспроданных лотов) — у `sold_out` и `expired`.

`server_time` берётся из Postgres и приходит всегда: таймер на фронте считается
как `expires_at − server_time`, чтобы не зависеть от часов браузера.

### Демо-ручки

Доступны только при `DEMO_ENABLED=true`: `expire-now` сжигает все выданные
права на товар, `simulate` заводит до 100 покупателей — на публичном стенде это
кнопка «сломать демонстрацию».

| Метод | Путь | Описание |
|---|---|---|
| `POST` | `/demo/items/:id/expire-now` | Сдвинуть срок всех прав на товар в прошлое |
| `POST` | `/demo/simulate` | `{"item_id": "...", "count": 50}` — N конкурентных претендентов через настоящий вход в очередь |

### Админские ручки

Редактирование каталога закрыто ключом: заголовок `X-Admin-Key: <ADMIN_SECRET_KEY>`
на каждом запросе. Отдельной админской сессии нет — для внутреннего инструмента
команды ключ и есть пропуск. Сессия обычного пользователя при этом тоже нужна:
админские маршруты лежат внутри той же группы `/api/v1`, что и остальное API.

| Метод | Путь | Описание |
|---|---|---|
| `POST` | `/admin/login` | Проверить ключ. Токена не выдаёт: фронт просто запоминает введённый ключ и шлёт его заголовком |
| `POST` | `/admin/catalog` | Создать товар. Вектор для похожих лотов считается сразу при создании |
| `PATCH` | `/admin/catalog/:id` | Изменить товар. При смене названия или категории вектор пересчитывается, старый выбрасывается из кэша |
| `DELETE` | `/admin/catalog/:id` | Мягкое удаление (`deleted_at`) |

Коды ответов: `403 ADMIN_FORBIDDEN` — ключ неверный или отсутствует,
`503 ADMIN_DISABLED` — `ADMIN_SECRET_KEY` не задан на сервере.

### Ограничение частоты

Две ручки закрыты счётчиком в памяти процесса — этого достаточно против случайного
перебора и «залипшей» кнопки, а от распределённой атаки MVP и не защищается:

| Путь | Лимит | Ключ |
|---|---|---|
| `POST /admin/login` | 10 запросов / 5 минут | IP |
| `POST /catalog/:id/queue` | 10 запросов / минуту | IP + товар |

Лимит на вход в очередь именно по паре «IP + товар»: за одним NAT сидят разные
покупатели, и общий лимит по IP отрезал бы честных участников очереди.

### Ошибки

Единый формат на всё API:

```json
{ "code": "NO_PURCHASE_RIGHT", "message": "У вас нет активного права на покупку этого товара" }
```

`code` — стабильная строка для ветвления на клиенте, `message` — текст для
человека. Коды: `INVALID_ITEM_ID`, `UNAUTHORIZED`, `INVALID_SESSION`,
`ITEM_NOT_FOUND`, `NO_PURCHASE_RIGHT`, `ITEM_SOLD_OUT`, `ALREADY_IN_QUEUE`,
`NOT_IN_QUEUE`, `CANNOT_LEAVE_QUEUE`, `STATUS_CONFLICT`, `INVALID_REQUEST_BODY`,
`INTERNAL_SERVER_ERROR`.

## Сценарий проверки

Основной путь кейса проверяется за пару минут без чтения кода. Переключатель
демо-пользователей в шапке приложения (Аня/Борис/Вера) — это независимые
подписанные сессии, второй браузер не нужен.

1. **Конкуренция за последнюю единицу.** Под Аней откройте товар с остатком 1
   («Виниловая пластинка Nier: Automata» или «Артбук The Art of Cyberpunk
   2077») и нажмите «Встать в очередь» — Аня сразу получает право и таймер.
   Переключитесь на Бориса, встаньте в очередь на тот же товар — Борис ждёт с
   позицией 1.
2. **Истечение права.** Не оплачивая под Аней, дождитесь конца таймера (90
   секунд) — или сожгите право сразу: `POST
   /api/v1/demo/items/:id/expire-now`. Право Ани сгорает, слот автоматически
   переходит Борису; Аня видит экран «право истекло» с похожими лотами и может
   встать заново.
3. **Покупка и sold_out.** Оплатите под Борисом — покупка завершена. Аня (если
   стояла в очереди) видит `sold_out` с предложением аналогов.
4. **Обход очереди невозможен.** Покупка без права отклоняется и по прямому
   URL, и по прямому запросу к API:

   ```
   curl -X POST http://localhost:8080/api/v1/catalog/<id>/purchase \
     -H "Authorization: Bearer <токен из /demo/login>"
   → 403 {"code":"NO_PURCHASE_RIGHT", ...}
   ```

5. **Стенд честности** (страница «Симулятор»): N параллельных входов в очередь
   через реальный API. Право получают ровно столько пользователей, сколько
   свободных единиц, — больше не позволяет констрейнт
   `catalog_items_stock_invariant` в схеме БД.
6. **Настройка правил очереди** (<http://localhost:3000/admin>, ключ
   `admin-local-dev-key`): заведите товар с тиражом 1 и окном на оплату 30
   секунд — и повторите пункты 1–3 на нём. Правила очереди задаются на товар, а
   не зашиты в код. Там же видно, сколько человек ждёт по каждому товару.

Автотестами это тоже закрыто: `internal/services/queue_entry_test.go` гоняет
конкуренцию поверх настоящего Postgres — 100 параллельных входов на товар с
одной единицей, 60 на товар с четырьмя, 20 одновременных оплат по одному праву
и сквозной сценарий, где 30 претендентов на 3 единицы разом входят в очередь и
разом оплачивают. Результат стабильно один и тот же: прав выдано ровно по
остатку, покупок ровно по остатку, счётчики товара сходятся с содержимым
`queue_entries`, ни одной ошибки констрейнта (сценарий приёмки A-04/A-09):

```
тираж 1, претендентов 100 → выдано прав 1, ждут 99, счётчики товара granted=1 used=0
тираж 4, претендентов 60  → выдано прав 4, ждут 56, счётчики товара granted=4 used=0
20 одновременных оплат по одному праву → успешных покупок: 1
тираж 3, претендентов 30  → покупок 3, счётчики товара granted=0 used=3
```

## Продуктовая логика

Право на покупку — не техническая деталь, а прямой ответ на бизнес-проблему
кейса: асинхронная оплата даёт заказов больше, чем единиц товара, пользователь
тратит время впустую, а площадка теряет доверие и получает лишнюю нагрузку.
Правила права выбраны так, чтобы закрывать это напрямую, а не «для красоты»:

- **Временное.** Если бы право не сгорало, один нерешительный покупатель мог
  бы держать дефицитный товар в подвешенном состоянии бесконечно — это тот же
  overselling-риск, только растянутый во времени вместо гонки запросов.
  Ограниченное окно на оплату гарантирует, что слот либо конвертируется в
  продажу, либо быстро возвращается тем, кто ещё ждёт.
- **Персональное и непередаваемое.** Если бы право можно было передать или
  подделать через `user_id`, вокруг дефицита тут же вырос бы вторичный рынок
  прав — именно то давление, ради снятия которого очередь и вводится.
  Привязка к подписанной сессии делает это невозможным технически, а не по
  договорённости.
- **Одноразовое.** Без атомарной проверки «уже потрачено» повторный вызов
  оплаты — обычный клиентский ретрай при плохой сети — превратился бы во
  вторую продажу того же слота.
- **FIFO с честной позицией.** Порядок, который пользователь может
  проверить сам («я третий, а не просто жду»), превращает ожидание из
  раздражения в понятную сделку — доверие к очереди держится на её
  предсказуемости, а не на пояснениях от площадки.
- **Явное состояние на каждом шаге.** Пользователь либо получает право и
  видит таймер, либо явное `sold_out` с альтернативой, либо `expired` с
  возможностью встать заново — нигде нет паузы без объяснения, где
  единственная мысль пользователя «а вдруг меня обманули».

Механика не привязана к конкретному товару из демо-каталога — она применима
к любому сценарию Авито с резким превышением спроса над предложением:
распродажи, лимитированные коллекции, билеты, объявления, которые разбирают
за минуты. Эффект один и тот же: меньше неудачных попыток покупки (либо
честная позиция, либо сразу альтернатива вместо разочарования в конце пути),
меньше пиковой нагрузки на чекаут за счёт того, что к оплате одновременно
допущено ровно столько пользователей, сколько есть единиц товара, и меньше
задвоенных/ошибочных заказов на стороне бизнеса.

## Чем занят пользователь в очереди

Ожидание — самое хрупкое место сценария: пользователь, который не понимает,
сколько ещё ждать и стоит ли, просто уходит. Поэтому экран ожидания отвечает на
три вопроса, и все три — данными, а не анимацией.

**Шанс на покупку.** Вместо обратного отсчёта «примерно 4 минуты» показывается
вероятность того, что очередь дойдёт: `P(Binomial(ahead, c) < unitsLeft)`, где
`ahead` — сколько человек впереди, `unitsLeft` — остаток тиража, а `c` —
**измеренная** конверсия права в покупку. Конверсия берётся по этому товару,
если завершённых прав набралось хотя бы пять; иначе общая по системе; иначе 0.5.
Источник приходит в ответе полем `basis` (`item` / `global` / `default`), и фронт
обязан их различать — выдавать предположение за измерение нельзя. Тот же расчёт
показывается на карточке товара **до** входа в очередь (`chance_if_join`): человек
решает, вставать ли, до того как потратит время.

Почему шанс, а не `eta_seconds`: честная оценка времени требует данных, которых
в MVP нет, а формула по позиции давала бы уверенно выглядящее неверное число.
Вероятность отвечает на тот же вопрос («стоит ли мне ждать») и не притворяется
точной.

**Прогресс.** У записи в очереди хранится `initial_position`, и на её фоне видно
движение: «было 12-м, стал 7-м» — очередь живая, а не зависшая.

**Похожие лоты прямо во время ожидания.** Не только на экране «товар закончился»:
альтернатива, предложенная заранее, — это ответ на вопрос кейса «почему
пользователь останется на платформе». Ушедший к аналогу покупатель остался
покупателем.

Конверсия для шанса кэшируется в памяти на 30 секунд. Ручку статуса поллят раз в
секунду все ожидающие одновременно, и агрегат на каждый опрос был бы ровно той
нагрузкой, ради снятия которой очередь и вводится.

## Админ-панель

Правила очереди должны быть настраиваемыми, иначе «команда сама определяет
правила» превращается в константы в коде.

Адрес — <http://localhost:3000/admin>, вход по значению `ADMIN_SECRET_KEY`
(в compose по умолчанию `admin-local-dev-key`). Ссылки в шапке нет намеренно:
это внутренний инструмент, а не часть пользовательского сценария.

Что можно делать:

- заводить, править и удалять товары;
- задавать **окно на оплату** отдельно каждому товару (`hold_ttl_seconds`) —
  дефицитной кроссовке нужны секунды, а редкой книге спокойные минуты;
- задавать тираж (`total_stock`), то есть сколько прав живёт одновременно;
- смотреть метрики по очередям: сколько ждут, у скольких право, сколько осталось.

Ключ хранится в памяти вкладки, перезагрузка страницы разлогинивает — для
инструмента, живущего внутри демо-стенда, это приемлемо, а `localStorage` с
админским ключом на публичном стенде хуже.

## ИИ в продукте

ИИ используется в двух местах, и они разного веса.

**Векторный подбор похожих лотов — основная ИИ-функция, работает в проде.**
Название и категория каждого товара превращаются в вектор через GigaChat
Embeddings, вектор лежит в колонке `catalog_items.embedding` (pgvector, HNSW-индекс
по косинусной близости), и подбор альтернатив — это один индексированный запрос
`ORDER BY embedding <=> ...` с фильтром «не распродано». Распроданное взамен
распроданного не предлагается.

Ключевое здесь — **когда** вызывается модель. Векторы считаются один раз: на
старте приложения (прогрев по товарам без вектора) и при создании или
переименовании товара в админке. На пользовательский запрос LLM не вызывается
никогда, в том числе в момент, когда экран «товар закончился» одновременно видят
все ожидавшие. Дополнительно вектора кэшируются в файл
`configs/embeddings_cache.json`, поэтому перезапуск контейнера не оплачивается
повторно. Внутри транзакции с блокировкой строки товара обращений к модели нет и
быть не может (INV-7) — ИИ-функции работают на данных, прочитанных после COMMIT.

**Текстовая рекомендация на экране `sold_out` — только в dev-режиме.** Короткая
реплика «не уходите, посмотрите похожие» генерируется GigaChat через плагин
dev-сервера Vite (`frontend/gigachat.plugin.ts`), то есть работает под
`npm run dev` с ключом в `frontend/.env.local` и **в прод-сборку не попадает**:
статику отдаёт nginx, эндпоинта `/ai/recommendation` там нет. Без ответа фича
молча гаснет, распределение прав от неё не зависит. Честный статус — это
незакрытый долг: рекомендацию нужно перенести в Go-бэкенд, чтобы она жила и в
Docker-сборке.

## Ключевые решения

### Почему одна база и почему PostgreSQL

Суть задачи — атомарная выдача ограниченного ресурса. Это требует транзакций и
блокировок строк, которые Postgres даёт напрямую. Второе хранилище превратило
бы локальную транзакцию в распределённую и создало бы второй источник истины
там, где нагрузка MVP этого не требует.

Защита от оверселла построена так:

1. Любая операция, меняющая распределение прав, начинается с
   `SELECT ... FOR NO KEY UPDATE` по строке товара. Все операции по одному
   товару сериализуются, разные товары друг другу не мешают. Именно
   `FOR NO KEY UPDATE`, а не `FOR UPDATE`: последний конфликтует с
   `FOR KEY SHARE`, который Postgres берёт на родительскую строку при вставке
   права с внешним ключом.
2. На товаре живут счётчики `granted_count`/`used_count` и констрейнт
   `CHECK (granted_count + used_count <= total_stock)`. Гарантия даётся схемой,
   а не аккуратностью кода: даже будущая ошибка в логике не продаст товар двоим.
3. Единый порядок блокировок во всех сценариях — `catalog_items → queue_entries`,
   поэтому взаимная блокировка невозможна в принципе.
4. Состояние участия живёт в одной строке `queue_entries` (от входа в очередь до
   финального исхода), а счётчики товара двигает **тот же оператор**, который
   меняет статус. Забыть обновить одно из двух невозможно: это физически один
   запрос.

Рассмотренные и отвергнутые альтернативы: `SERIALIZABLE` (корректно, но требует
retry-цикла на `40001` во всех вызывающих местах), `REPEATABLE READ` (не
работает — «посчитать свободные слоты и вставить права» это write skew, который
Postgres ловит только на `SERIALIZABLE`), один «умный» `INSERT ... SELECT`
(без блокировки две транзакции видят одинаковый снимок и обе считают один и тот
же слот свободным), мьютекс в Go (умирает на второй реплике).

### Почему срок жизни права хранится в базе, а не в Redis

Истечение права имеет побочный эффект: слот должен вернуться в пул и уйти
следующему в очереди, то есть это транзакция в основной базе. Уведомления об
истечении ключей в Redis доставляются без гарантий, и потерянное при перезапуске
событие означало бы навсегда заблокированный слот. Срок хранится колонкой
`expires_at`, право активно при `status = 'granted' AND expires_at > now()`.

Все доменные сроки и порядок FIFO считает Postgres. `time.Now()` в Go для этого
не используется: `created_at` — ключ сортировки очереди, и часы приложения в
этой роли означали бы, что на второй реплике FIFO молча перестаёт быть FIFO.

### Почему нет фоновых воркеров

Очередь продвигается лениво: любая операция, которая читает или меняет
состояние (включая поллинг статуса), сначала гасит истёкшие права и раздаёт
освободившиеся слоты. Перед этим выполняется дешёвая проверка без блокировки —
есть ли вообще работа, — поэтому частый поллинг не превращает блокировку строки
товара в горячую точку. Отдельный воркер потребовал бы лидер-выборов при
масштабировании и дал бы то же самое с задержкой.

### Почему поллинг, а не WebSocket

Поток данных односторонний и низкочастотный, а поллинг раз в секунду вдобавок
служит естественным триггером продвижения очереди. SSE рассматривается как
улучшение после закрытия обязательного объёма.

### Почему не микросервисы

Разделение каталога и очереди по сервисам с отдельными базами превратило бы
локальную транзакцию в распределённую — то есть создало бы ровно ту проблему,
которую задача просит решить. Разделение по зонам ответственности достигается
пакетами внутри монолита: `repository → services → handlers`, `domain` не
зависит ни от чего, интерфейсы репозиториев объявлены на стороне потребителя.

## Линтеры

Backend: golangci-lint, конфиг `.golangci.yaml` в корне. `golangci-lint run`.

- `govet`, `staticcheck`, `unused`, `ineffassign` — базовая гигиена и мёртвый код.
- `errcheck` — в Go легко молча проигнорировать ошибку; для сервиса, где
  корректность важнее скорости, это недопустимо.
- `rowserrcheck`, `sqlclosecheck` — ловят незакрытые `rows` и непроверенные
  ошибки после итерации: частый источник утечек соединений при работе через pgx.
- `noctx` — требует явной передачи `context.Context`, без чего не работают ни
  таймауты, ни корректное завершение.
- `forbidigo` с проектным правилом на `\.pool\.(Exec|Query|QueryRow)` — самое
  интересное правило набора. В репозиториях исполнитель запроса берётся только
  через `db(ctx, r.pool)`, который возвращает транзакцию из контекста, если она
  там есть. Прямое обращение к пулу внутри транзакции выполнило бы запрос **вне**
  неё: блокировка строки товара осталась бы в стороне, а изменение —
  незакоммиченным вместе с остальными. Такую ошибку почти невозможно заметить на
  ревью и очень трудно воспроизвести, поэтому она запрещена линтером.

Frontend: ESLint (flat config, type-checked) + Prettier + Stylelint —
`npm run lint`, `npm run format:check`, `npm run lint:css` в `frontend/`.

CI (`.github/workflows/lint.yml`) на каждый PR и пуш в main: golangci-lint,
интеграционные тесты бэкенда с настоящим Postgres и goose-миграциями под
`-race`, фронтовые ESLint + typecheck + Vitest.

  рекомендация на экране `sold_out` осталась dev-only.

## Ограничения MVP

Сознательно не реализовано (по условию кейса): настоящие регистрация и
авторизация, настоящая оплата, списание стоков, полноценное оформление заказа.
Личность пользователя существует ровно в объёме, необходимом для привязки права
на покупку, и выдаётся ручкой `/demo/login`.

Осознанные упрощения — что именно и почему:

| Ограничение | Почему так |
|---|---|
| `eta_seconds` всегда `null` | Честная оценка времени требует данных, которых нет; формула по позиции давала бы уверенно выглядящее неверное число. Ответ на тот же вопрос даёт `chance` |
| Похожие лоты требуют `GIGACHAT_AUTH_KEY` | Без ключа векторов нет, `/similar` отвечает `500`, `alternatives` пустые. Заготовленных векторов в сидах нет намеренно: они протухли бы при первой же правке каталога |
| Текстовая ИИ-рекомендация только в `npm run dev` | Прокси живёт в плагине dev-сервера Vite; в Docker её нет. Долг, а не решение — см. «ИИ в продукте» |
| Конверсия для шанса кэшируется в памяти процесса | Цифра справочная: расхождение между репликами на десяток секунд ни на что не влияет, а общее хранилище ради неё стоило бы дороже самой цифры |
| Ограничение частоты — счётчик в памяти процесса | Против перебора и залипшей кнопки работает, против распределённой атаки — нет. Для MVP осознанно |
| Ключ админки хранится в памяти вкладки | Перезагрузка разлогинивает. `localStorage` с админским ключом на публичном стенде хуже |
| Купивший товар может снова встать в очередь | История участий не удаляется, повторный вход создаёт новую запись. Для MVP приемлемо |
| Демо-личность живёт сутки | По истечении подписи фронт молча перелогинивается с новым `user_id`; старая очередь остаётся ничьей |
| Нет SSE/WebSocket | Поллинг раз в секунду вдобавок служит триггером ленивого продвижения очереди — см. «Ключевые решения» |
