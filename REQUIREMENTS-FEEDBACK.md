Требования на доработку по итогам полуфинала. Источник — обратная связь ментора
плюс решения, принятые командой при разборе.

Отношение к остальным документам: `docs/REQUIREMENTS.md` — исходный объём работ,
`REQUIREMENTS-PATCH.md` — уточнения по ходу разработки, этот файл — **что делаем
после полуфинала и до предзащиты 14 августа**. Исходные документы задним числом
не правим.

Приоритеты вместо MoSCoW: MoSCoW отвечает на вопрос «что войдёт в MVP», а здесь
объём уже сдан и вопрос другой — «что чинить первым».

| Приоритет | Значение |
|---|---|

## North star — обратная связь ментора

> На защите раскрыть техническую реализацию очереди, показать схемы и
> архитектуру. В проекте упор делается на устройство бэкенда, нужно рассказать
> как он работает, за счет чего выполняются требования к проекту.
>
> Что можно улучшить:
>
> 1. Стоять в очереди – скучно, пользователь уйдет не дождавшись, нужно
>    придумать чем его завлечь, чтобы время проходило легче.
> 2. Упростить модель данных: состояние покупки хранится одновременно в очереди,
>    правах и счётчиках товара. Если при новом переходе обновить не все три
>    места, пользователь может видеть выданное право, а товар считаться
>    свободным, либо слот останется заблокированным после истечения права.
> 3. Продумать настройку очереди: что можно настраивать, можно ли создавать
>    несколько очередей в разных частях Авито, предусмотреть админку или другие
>    варианты.
> 4. Пересмотреть применение GigaChat: сейчас он используется для простой
>    рекомендации, AI стоит применять для более сложных задач.
> 5. Оптимизировать рекомендации: сейчас они, как я понимаю, каждый раз
>    запрашиваются для каждого пользователя, что создает высокую нагрузку в
>    момент, когда всем ожидающим показывается экран окончания ожидания. Сделать
>    упор на оптимизацию и показать решения, которые делают фичу эффективнее.

Каждое требование ниже помечено номером пункта, на который отвечает.

## P0 — модель данных

### MDL-01. Одна запись на одно участие

`queue` и `purchase_rights` сливаются в `queue_entries`: одна строка — одно
участие пользователя в очереди на товар, от входа до финального исхода.

```sql
CREATE TABLE queue_entries (
    id               UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    item_id          UUID NOT NULL REFERENCES catalog_items(id),
    user_id          UUID NOT NULL,
    status           TEXT NOT NULL CHECK (status IN
                       ('waiting','granted','purchased','expired','cancelled','sold_out')),
    created_at       TIMESTAMPTZ NOT NULL DEFAULT now(),   -- ключ FIFO
    granted_at       TIMESTAMPTZ,
    expires_at       TIMESTAMPTZ,
    resolved_at      TIMESTAMPTZ,
    initial_position INT,                                   -- для WAIT-03
    CONSTRAINT queue_entries_granted_deadline CHECK (
        status <> 'granted' OR (granted_at IS NOT NULL AND expires_at IS NOT NULL))
);

CREATE UNIQUE INDEX queue_entries_active ON queue_entries (user_id, item_id)
    WHERE status IN ('waiting','granted');
CREATE INDEX queue_entries_fifo   ON queue_entries (item_id, status, created_at, user_id);
CREATE INDEX queue_entries_expiry ON queue_entries (item_id, expires_at) WHERE status = 'granted';
```

Констрейнт односторонний намеренно: у сгоревшего права `expires_at` остаётся —
на нём считается статистика.

**Почему:** пункт 2. Оба сценария ментора («видит право, товар свободен»,
«слот заблокирован») возникают из-за того, что состояние собирается из двух
таблиц по правилу «последняя запись», и после повторного входа эти записи могут
описывать разные попытки.

**Приёмка:**
- `internal/services/queue_concurrency_test.go` проходит без изменений в самом тесте;
- новый тест: истечение права → слот уходит следующему → счётчики совпадают
  с `SELECT count(*)` по статусам;
- инвариант **INV-5** удаляется из `CLAUDE.md`: синхронизировать больше нечего.

**Владелец:** Артём. **Блокирует:** ADM-01 (снимается через вью, см. ADM-01), WAIT-03.

### MDL-02. Стратегия миграции данных

Два варианта, решение принимается в момент наката.

| | Вариант A — пересоздать (по умолчанию) | Вариант B — перелить |
|---|---|---|
| Что делаем | Создаём таблицу пустой, на стенде `docker compose down -v` | `INSERT … SELECT` из старых таблиц с сопоставлением по времени |
| Объём | ~30 строк SQL | ~100 строк, из них половина — краевые случаи |
| Риск | Теряются демо-участия. Каталог не страдает: он в `catalog_items`, миграция `00004` не трогается | Ошибка в сопоставлении даёт неверные счётчики, ловится не сразу |
| Когда брать | Всегда, если на стенде только демо-данные | Только если на стенде есть что-то, что жалко потерять |

**Решение по умолчанию — A.** Данные на стенде демонстрационные (`Аня/Борис/Вера`
и записи симулятора), сохранять их незачем, а сложная миграция накануне защиты —
это риск без выгоды.

Порядок наката обязателен в обоих вариантах:

1. создать таблицу и индексы;
2. (вариант B) перелить данные — **до** создания триггера, иначе счётчики
   посчитаются дважды;
3. создать функцию и триггер MDL-03;
4. пересчитать `granted_count`/`used_count` одним `UPDATE` из `queue_entries`;
5. заменить вью `admin_queue_entries` на новую таблицу — **до** удаления старых,
   иначе `DROP TABLE` упрётся в зависимость, а `CASCADE` молча снесёт вью;
6. удалить `purchase_rights` и `queue`.

Номер миграции — `00006`. `00005` занята админкой (ADM-01), чтобы две ветки
не дрались за номер.

**Владелец:** Артём.

### MDL-03. Счётчики обновляет база

`granted_count` и `used_count` остаются на `catalog_items` вместе с
`CHECK (granted_count + used_count <= total_stock)` — это единственная форма, в
которой Postgres умеет декларативно гарантировать «не продать больше тиража».
Тираж в `queue_entries` не переносится: это свойство товара, а не участия.

Меняется одно: счётчики обновляет триггер на `queue_entries` по переходу
статуса. Все вызовы `CatalogRepo.AdjustCounts` из Go удаляются (сейчас их
четыре: два в `Reconcile`, один в `Leave`, один в `PurchaseRight.Buy`).

**Приёмка:** grep по `AdjustCounts` в `internal/services` пуст; после серии
входов, покупок и истечений счётчики равны `COUNT(*)` по соответствующим
статусам.

**Владелец:** Артём.

## P0 — рекомендации

### REC-01. Таблица-кэш

```sql
CREATE TABLE item_recommendations (
    item_id       UUID PRIMARY KEY REFERENCES catalog_items(id),
    candidate_ids UUID[] NOT NULL,
    ai_text       TEXT,        -- NULL = деградировали без ИИ, экран остаётся рабочим
    ai_payload    JSONB,       -- структурированный ответ AI-02
```

Чтение никогда не ходит в LLM: это `SELECT` по первичному ключу. Промах отдаёт
похожие лоты без текста ИИ и ставит задачу на пересчёт. TTL ~10 минут,
инвалидация по `input_hash` от пары (товар, набор кандидатов).

**Почему:** пункт 5.

**Приёмка:** `GET /catalog/:id/recommendation` при выключенном GigaChat
отвечает 200 со списком кандидатов и `ai_text: null`.

**Владелец:** Максим.

### REC-02. Один вызов на одновременный промах

Внутри процесса — `singleflight.Group` по `item_id`. Между репликами —
`pg_try_advisory_xact_lock(hashtext(item_id::text))`: не взял лок, значит кто-то
уже считает, отдаём фолбэк без ожидания.

**Приёмка:** 100 одновременных запросов на холодном кэше дают **один** вызов
провайдера — показать в логах, это цифра для защиты.

**Владелец:** Максим.

### REC-03. Прогрев до наплыва

В `Reconcile`, **после COMMIT** (INV-7: в транзакции с блокировкой нет
HTTP и LLM), если `total_stock - used_count <= 1` — асинхронно готовим
рекомендацию. К моменту, когда очередь увидит `sold_out`, строка уже лежит.

Без этого требование REC-01 не закрывает сценарий ментора: первая волна
запросов придёт на холодный кэш и всё равно уйдёт в нейросеть.

**Приёмка:** выкуп последней единицы на товаре с очередью → строка в
`item_recommendations` появляется до того, как первый пользователь увидит
`sold_out`.

**Владелец:** Максим.

### REC-04. Единый источник альтернатив

`alternatives` в конверте состояния и ручка `GET /catalog/:id/similar` читают
`candidate_ids` из `item_recommendations` вместо `GetSimilarItems` на каждый
опрос каждого ожидающего. На ручку — `Cache-Control: public, max-age=60` и ETag:
ответ одинаков для всех пользователей.

**Приёмка:** при 100 ожидающих на товаре в логах нет 100 запросов
`GetSimilarItems` в секунду.

**Владелец:** Максим.

## P1 — ожидание

### WAIT-01. Шанс на покупку

В конверте состояния для `waiting` приходит вероятность того, что очередь
дойдёт.

```
ahead      = granted_count + (position − 1)     // держатели прав + впереди в очереди
units_left = total_stock − used_count
c          = конверсия права в покупку (по товару → по системе → 0.5)
percent    = P( Binomial(ahead, c) < units_left ) × 100
```

Считается точно по CDF, без симуляции. `c` берётся из уже собираемой статистики
и кэшируется в памяти на 30 секунд — агрегат на каждый опрос повторил бы ровно
ту ошибку, за которую ментор ругал рекомендации (пункт 5).

Показываем **процент**, не время. Причина та же, по которой `eta_seconds`
остаётся `null`: ложная точность по времени хуже честной оценки шанса.

**Почему:** пункт 1. Ожидание перестаёт быть слепым — человек понимает, стоит
ли ждать, и решает сам.

**Приёмка:** на товаре с остатком 1 и тремя ожидающими третий видит низкий
шанс; после ухода двоих впереди — высокий.

**Владелец:** Артём (бэкенд), Егор (экран).

### WAIT-03. Прогресс очереди

Колонка `initial_position` заполняется на вставке записи. В конверте приходят
`initial_position` и `progress_percent = (initial − current) / (initial − 1) × 100`
(при `initial = 1` → 100). Фронт рисует полосу и текущий номер.

У записей, перелитых из старой схемы, `initial_position` пустой — полосу для них
не рисуем.

**Владелец:** Артём (бэкенд), Егор (экран).

### WAIT-04. Похожие лоты во время ожидания

Экран ожидания показывает похожие лоты с формулировкой «место в очереди
сохранится». Бэкенд не меняется: ручка `GET /catalog/:id/similar` уже есть и уже
используется на экране `sold_out`; после REC-04 она начнёт читать кэш, контракт
при этом не изменится.

**Почему:** пункт 1 — план Б готовится во время ожидания, а не подсовывается в
момент разочарования.

**Владелец:** Егор.

### Контракт для фронта

Конверт состояния (`GET/POST/DELETE /catalog/:id/queue[/me]`), поля
добавляются, существующие не меняются:

```json
{
  "status": "waiting",
  "message": "Вы в очереди...",
  "position": 6,
  "initial_position": 9,
  "progress_percent": 37,
  "queue_size": 14,
  "expires_at": null,
  "server_time": "2026-08-12T20:15:00+03:00",
  "eta_seconds": null,
  "next_step": { "kind": "wait", "label": "..." },
  "alternatives": [],
  "chance": { "percent": 72, "basis": "item" }
}
```

| Поле | Тип | Когда | Смысл |
|---|---|---|---|
| `initial_position` | int \| null | `waiting`, `granted` | позиция на входе, не меняется |
| `progress_percent` | int 0–100 | `waiting` | насколько продвинулся |
| `chance.percent` | int 0–100 | `waiting` | шанс, что очередь дойдёт |
| `chance.basis` | `item` \| `global` \| `default` | с `percent` | на чьей конверсии считали |

Карточка товара (`GET /catalog/:id`): `"chance_if_join": { "percent": 45, "basis": "global" }`.

## P1 — настройка и админка

### CFG-01. Условие включения очереди

Очередь применяется не ко всем товарам, а к дефицитным. Две колонки на
`catalog_items`:

```sql
queue_threshold INT     NOT NULL DEFAULT 5,   -- очередь включается при total_stock <= threshold
queue_enabled   BOOLEAN                        -- NULL = авто по порогу, true/false = принудительно
```

`queue_enabled` отдаётся в DTO товара: карточка показывает «Купить» вместо
«Встать в очередь», экран ожидания не открывается.

**Почему:** пункт 3, и прямая формулировка кейса — обход очереди проверяется,
«если она действует для товара».

**Владелец:** Григорий.

---

### CFG-02. Настройка окна на оплату

`hold_ttl_seconds` (колонка уже есть) редактируется из админки. Короткое окно
ускоряет оборот слота, длинное снижает долю сгоревших прав; для дорогих
категорий нужно больше времени на решение.

**Владелец:** Григорий.

### ADM-01. Ручки админки

```
GET   /admin/items             список: тираж, в очереди, держат право, свободно, конверсия
GET   /admin/items/:id/queue   визуализация очереди по товару
PATCH /admin/items/:id         { queue_enabled, queue_threshold, hold_ttl_seconds }
```

```json
// GET /admin/items/:id/queue
{
  "server_time": "...",
  "item": { "total_stock": 5, "granted_count": 2, "used_count": 1, "stock_left": 2,
            "hold_ttl_seconds": 90, "queue_enabled": true, "queue_threshold": 5 },
  "holders": [ { "user_id": "...", "granted_at": "...", "expires_at": "...", "seconds_left": 47 } ],
  "waiting": [ { "user_id": "...", "position": 1, "waiting_seconds": 132 } ],
  "recent":  [ { "user_id": "...", "status": "expired", "resolved_at": "..." } ]
}
```

`seconds_left` считается от `server_time` из Postgres, не от часов Go (INV-6).

**Развязка с MDL-01.** Админка читает не таблицы, а вью со стабильными
колонками — тогда слияние таблиц её не ломает:

```sql
-- миграция 00005
CREATE VIEW admin_queue_entries AS
SELECT q.item_id, q.user_id, q.status, q.created_at,
       r.created_at AS granted_at, r.expires_at
FROM queue q
LEFT JOIN LATERAL (
    SELECT created_at, expires_at FROM purchase_rights pr
    WHERE pr.user_id = q.user_id AND pr.item_id = q.item_id AND pr.status = 'granted'
    ORDER BY pr.created_at DESC LIMIT 1
) r ON true
WHERE q.status IN ('waiting', 'granted');
```

После MDL-01 тело вью заменяется на выборку из `queue_entries` с теми же
колонками — код админки не меняется.

### AI-02. Ранжирование вместо подписи

Модель не пишет текст к готовому списку, а выбирает и упорядочивает: на вход —

### AI-04. Похожие лоты по эмбеддингам

Товары превращаются в векторы, похожесть считается косинусом. Даёт то, чего не
даёт фильтр по категории: связь поперёк категорий (винил по вселенной →
артбук по ней же) и устойчивость к тому, что категория проставлена криво.

Почему это лучше, чем спрашивать модель «какой товар похож» на каждый запрос:
вызов нейросети уходит из горячего пути совсем, ответ детерминирован и
кэшируется, модель не может назвать несуществующий `item_id`. То есть решение
отвечает сразу на пункт 4 (нетривиальная задача для AI) и на пункт 5
(нагрузка не зависит от числа пользователей).

**Условия, без которых не берём:**

1. **Без pgvector.** Вектор хранится в `REAL[]`, косинус считается в Go — на
   объёме каталога это микросекунды. pgvector требует замены образа Postgres в
   docker-compose, то есть правки общей инфраструктуры накануне защиты ради
   выигрыша, которого на таком объёме нет. Допустимо, только если уезжает
   заранее и не в последний вечер.
2. **Считаем офлайн.** Эмбеддинги строятся при старте или по ручке админки,
   результат лежит в БД. В обработке запроса вызовов модели нет (INV-7). Нет
   вектора — молча падаем на текущий фильтр по категории.
3. **Стыковка с REC-01, а не параллельный путь.** Выход — упорядоченный
   `candidate_ids` в `item_recommendations`. Двух конкурирующих источников
   похожих лотов быть не должно.

**Приёмка:** в сидах есть пара товаров, похожих поперёк категорий, и на экране
`sold_out` они предлагаются — иначе результат неотличим от `WHERE category = $1`
и показать на защите нечего.

**Приоритет:** ниже админки. Сначала ADM-01/02 доведены до рабочего состояния,
эмбеддинги — только после.

**Владелец:** Григорий.

### CFG-03. Политики очереди на область каталога

Очередь как политика, применяемая к товару, продавцу, категории или кампании;
выигрывает самая узкая область. Это ответ на вопрос ментора «можно ли создавать
несколько очередей в разных частях Авито».

```sql
CREATE TABLE queue_policies (
    id          UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    name        TEXT NOT NULL,
    scope_type  TEXT NOT NULL CHECK (scope_type IN ('item','category','seller','campaign','global')),
    scope_id    TEXT,
    mode        TEXT NOT NULL CHECK (mode IN ('fifo','lottery','auction')),
    params      JSONB NOT NULL DEFAULT '{}',
    active_from TIMESTAMPTZ,
    active_to   TIMESTAMPTZ,
    enabled     BOOLEAN NOT NULL DEFAULT true
);
```

Реализуем, только если закрыты P0 и P1. Иначе показываем схемой на слайде как
спроектированное — это честнее полусырой реализации.

### CFG-04. Режимы выдачи слотов

Выбор «кому отдать освободившиеся слоты» выносится за интерфейс:

```go
type SlotAllocator interface {
    SelectNext(ctx context.Context, itemID uuid.UUID, slots int) ([]uuid.UUID, error)
}
// fifo    → ORDER BY created_at, user_id
// lottery → ORDER BY hashtext(user_id::text || drop_seed)  -- случайно, но воспроизводимо
// auction → ORDER BY bid_amount DESC, created_at
```

Сейчас порядок зашит в `QueueRepo.GetWaiting`. Инварианты атомарности от режима
не зависят — меняется только порядок, поэтому добавление режима не трогает
логику, отвечающую за «не продать дважды».

## Чего не делаем

- Не добавляем брокеры, Redis, фоновые воркеры — «одно хранилище, один источник
  истины» остаётся частью обоснования выбора БД.
- Не заменяем поллинг на WebSocket/SSE: опрос раз в секунду — триггер ленивого
  продвижения очереди.
- Не показываем оценку времени ожидания в секундах: `eta_seconds` остаётся
  `null`, честный ответ — процент шанса (WAIT-01).
- Не геймифицируем ожидание. Пункт 1 закрывается полезной информацией и планом Б,
  а не развлечением.
- Не правим применённые миграции: изменения только новыми номерами.
