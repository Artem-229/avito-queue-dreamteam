# CLAUDE.md

Рабочий документ для ИИ-агентов и разработчиков: **инварианты системы, текущее состояние,
известные ограничения**. Исторический реестр дефектов (D-01…D-14, B-01…B-14) удалён —
все перечисленные в нём блокеры закрыты; хронология исправлений видна в истории git.

Навигация по репозиторию и HTTP-контракт — [AGENTS.md](./AGENTS.md).
Требования — `docs/REQUIREMENTS.md` + `REQUIREMENTS-PATCH.md`.

## 1. Инварианты системы

Формулировки нормативны. Правка, которая их ослабляет, — дефект, даже если тесты зелёные.

* **INV-1.** `granted + used <= total_stock` для каждого товара при любой конкуренции.
  Проверяется констрейнтом `catalog_items_stock_invariant`, а не только кодом.
* **INV-2.** Распределение прав меняют только `QueueEntryService.Reconcile`,
  `QueueEntryService.Leave` и `QueueEntryService.Buy`. Новых мест не создавать.
* **INV-3.** Любая мутация распределения начинается с `CatalogRepo.LockItem`
  (`SELECT ... FOR NO KEY UPDATE`) в той же транзакции. Порядок блокировок один:
  `catalog_items → queue_entries`.
* **INV-4.** В `repository` запрос выполняется только через `db(ctx, r.pool)`. Прямой
  `r.pool.Exec/Query/QueryRow` запрещён линтером `forbidigo`.
* **INV-5.** Счётчики `catalog_items.granted_count/used_count` меняются **тем же оператором**,
  что и статус участия (CTE `counters`), с дельтами из `counterDeltas(from, to)`. Отдельного
  вызова «поправить счётчик» из Go не существует. Раньше этот инвариант звучал как
  «`purchase_rights.status` и `queue.status` меняются в одной транзакции» — после слияния
  таблиц синхронизировать нечего, осталась только проекция счётчиков.
* **INV-6.** Доменные сроки считает Postgres (`now()`, `make_interval`), `created_at` очереди
  заполняется `DEFAULT now()` самой базой. `time.Now()` в Go — только логи, метрики и подпись
  сессии.
* **INV-7.** Внутри транзакции с блокировкой нет HTTP-вызовов, обращений к LLM и `time.Sleep`.
* **INV-8.** У каждого состояния, отдаваемого фронту, есть `message` и `next_step`.
  Отсутствие записи в очереди — тоже состояние (`not_in_queue`), а не 404.
* **INV-9.** Все сравнения с остатком нестрогие (`>=`, `<=`), никогда `==`.
* **INV-10.** FIFO детерминирован: выдача (`GrantNext`) и вычисление позиции (`Snapshot`)
  идут по одному ключу `(created_at, user_id)`.
* **INV-11.** Переходы статусов — только CAS: `UPDATE ... WHERE status = <from>`,
  ноль затронутых строк — ошибка `ErrStatusConflict`, а не «нечего делать».

## 2. Текущее состояние

Основной сценарий кейса проходится целиком и проверен вручную и тестами:
вход в очередь → выдача права по FIFO → таймер → покупка / истечение → слот следующему →
`sold_out` с альтернативами. Конкурентность закрыта интеграционными тестами
(`internal/services/queue_concurrency_test.go`): 100 параллельных входов на товар
с одной единицей дают ровно одно право.

Что важно знать агенту перед правками:

* **Одна таблица состояния.** `queue` и `purchase_rights` слиты в `queue_entries`
  (миграция `00006`): одна строка — одно участие. Право на покупку как отдельная сущность
  в хранилище не существует. `services/queue.go`, `services/purchase_right.go`,
  соответствующие репозитории и хендлер удалены, их заменяет
  `QueueEntryService` + `QueueEntryRepository`.
* Персональность права держится на подписанной сессии (HMAC-SHA256, `internal/infra/http/rest/session`).
  Неподписанного пути идентификации (`X-User-Id` и т.п.) не существует вовсе.
* Продвижение очереди ленивое: `EnsureAdvanced` (дешёвый `NeedsReconcile` без блокировки →
  `Reconcile` при необходимости) вызывается из `Entry`, `Status`, `Leave` и `Buy`. Фоновых
  воркеров нет — это осознанное решение, описанное в README.
* **Конверт статуса собирает `buildResponse`** — единственное место, где состояние
  превращается в ответ фронту. Данные для него приходят одним `Snapshot`: участие, позиция,
  размер очереди, время сервера и счётчики товара. Отдельный поход в каталог из горячего пути
  убран намеренно — ручку поллят раз в секунду все ожидающие.
* **Шанс на покупку** (`services/chance.go`) — `P(Binomial(ahead, c) < unitsLeft)`, где `c` —
  измеренная конверсия права в покупку: по товару при выборке от 5 завершённых прав, иначе
  общая по системе, иначе 0.5. Конверсия кэшируется в памяти на 30 секунд; агрегат на каждый
  опрос был бы той самой нагрузкой, за которую ругали рекомендации.
* Похожие лоты (`/similar` и `alternatives` в конверте) подбираются по векторной близости
  (pgvector, `catalog_items.embedding`); распроданные (`used_count >= total_stock`)
  не предлагаются.
* Тесты доменной логики интеграционные и требуют живой Postgres; без него скипаются.
  DSN — `TEST_DATABASE_DSN`, при запуске через compose порт **5433** (см. README «Тесты»).

## 3. Известные ограничения (осознанные, не дефекты)

| Что | Почему так |
|---|---|
| `eta_seconds` всегда `null` | Честная оценка времени требует данных, которых нет; формула по позиции давала бы уверенно выглядящее неверное число. Ответ на тот же вопрос даёт `chance` — он опирается на измеренную конверсию и отдаёт вероятность, а не выдуманные секунды |
| Конверсия для шанса кэшируется в памяти процесса | Цифра справочная: расхождение между репликами на десяток секунд ни на что не влияет, а общее хранилище ради неё стоило бы дороже самой цифры |
| Купивший товар может снова встать в очередь | Записи истории не удаляются; повторный вход после покупки создаёт новую запись, и статус-конверт показывает её, а не `purchased`. Для MVP приемлемо |
| `/demo/*` включаются флагом `DEMO_ENABLED` | В compose включены для демонстрации; на публичном стенде решить отдельно — `expire-now` сжигает права всех пользователей товара |
| Демо-личность живёт сутки | По истечении подписи фронт молча перелогинивается с новым `user_id`; старая очередь остаётся ничьей |

## 4. Чего не делать

* Не переписывать архитектуру: слои, DI, интерфейсы на стороне потребителя, сентинел-ошибки —
  всё в порядке.
* Не заводить отдельный вызов правки счётчиков товара и не возвращать `AdjustCounts` в
  сервисы: счётчик двигается тем же оператором, что и статус (INV-5).
* Не разносить состояние участия обратно по нескольким таблицам и не добавлять полей,
  дублирующих `queue_entries.status`.
* Не добавлять брокеры, Redis, ORM, фоновые воркеры. «Одно хранилище, один источник истины» —
  часть обоснования выбора БД в README.
* Не вызывать LLM, HTTP и `time.Sleep` внутри транзакции с блокировкой (INV-7). ИИ-фичи
  работают на данных, прочитанных **после** COMMIT.
* Не менять `docs/REQUIREMENTS.md` задним числом — уточнения через `REQUIREMENTS-PATCH.md`.
* Не заменять поллинг на SSE/WebSocket: поллинг раз в секунду — триггер ленивого продвижения
  очереди, это осознанное решение из README.
* Не редактировать применённые миграции (кроме сидов `00004` на этапе разработки —
  после правки сидов нужен `docker compose down -v`).

## 5. Чек-лист проверки перед сдачей

1. `docker compose up -d --build` с чистого тома → фронт на :3000, API на :8080.
2. Два браузера (или переключатель демо-пользователей): двое на товар с одной единицей —
   право у одного, второй видит позицию.
3. `/demo/items/:id/expire-now` → слот уходит второму без новых входов в очередь.
4. `POST /catalog/:id/purchase` без права через curl → `403 NO_PURCHASE_RIGHT`.
5. Счётчики сходятся с содержимым таблицы после серии входов, покупок и истечений:
   `SELECT granted_count, used_count FROM catalog_items WHERE id = ...` против
   `SELECT status, count(*) FROM queue_entries WHERE item_id = ... GROUP BY status`.
6. `go test -count=1 ./internal/...` с `TEST_DATABASE_DSN` на :5433 — зелёные.
7. `golangci-lint run`, в `frontend/`: `npm run lint && npm run typecheck && npm run test`.
