## 1. Стек

| Слой | Выбор | Почему |
|---|---|---|
| Сборка | Vite 5 | Требование кейса допускает Vite; мгновенный HMR, простой multi-stage Docker |
| Язык | TypeScript 5, `strict: true` | Требование кейса |
| UI | React 18 | Требование кейса |
| Роутинг | React Router v6 (data router) | Нужны guard'ы на `/checkout` — защита от обхода очереди |
| Серверный стейт | TanStack Query v5 | Кэш, ретраи, инвалидация; SSE-события пишем прямо в кэш |
| Клиентский стейт | Zustand | Текущий «пользователь» демо-режима, тосты, UI-флаги. Без бойлерплейта Redux |
| Стили | CSS Modules + дизайн-токены в CSS-переменных | Полный контроль над «стилем Авито», нулевой рантайм, нет борьбы с чужой темой |
| Реалтайм | нативный `EventSource` (SSE) + polling-фолбэк | Поток односторонний, SSE проще WebSocket и переживает reverse-proxy |
| Моки | MSW (Mock Service Worker) | Фронт не ждёт бэкенд; те же моки переиспользуются в тестах |
| Тесты | Vitest + React Testing Library | Требование жюри «наличие тестов» |
| Линт | ESLint 9 flat config + Prettier + Stylelint | Требование жюри «линтеры с правилами и обоснованием» |
| Деплой | multi-stage Dockerfile → nginx (статика + proxy `/api`) | Требование docker-compose |

**Почему не MUI/AntD:** дефолтная тема этих китов узнаваема, жюри увидит «библиотечный» интерфейс вместо айдентики Авито. Своя мини-система из 8–10 компонентов пишется за пару часов и даёт максимум баллов за «дизайн и архитектуру».

## 3. Стейт-машина очереди

Единственный источник правды о том, что рисовать. Бэкенд возвращает `status`, фронт нигде не вычисляет статус сам.

```
                       ┌──────────────────────────────────────┐
                       │                                       │
  IDLE ──join──▶ QUEUED ──выбор системы──▶ GRANTED ──checkout──▶ PURCHASED
    ▲              │                          │
    │              │                          └──ttl истёк──▶ EXPIRED ──▶ (снова в очередь / выход)
    │              │
    │              ├──товар кончился──▶ SOLD_OUT ──▶ рекомендации аналогов
    │              │
    └──────leave───┘
```

| Статус | Что видит пользователь | Следующий шаг |
|---|---|---|
| `IDLE` | Карточка товара, кнопка «Встать в очередь» | Нажать кнопку |
| `QUEUED` | Позиция N из M, прогресс-бар, AI-прогноз «≈ 2 мин», кнопка «Выйти из очереди» | Ждать, страницу можно закрыть |
| `GRANTED` | Крупный таймер (по умолчанию 120 c), зелёный бейдж «Право на покупку ваше», кнопка «Перейти к оплате» | Оформить до истечения таймера |
| `EXPIRED` | «Время вышло, право передано следующему», объяснение правил | Встать в очередь заново или посмотреть аналоги |
| `PURCHASED` | Экран успеха, номер заказа | Вернуться в каталог |
| `SOLD_OUT` | «Товар разобрали», честное объяснение | AI-подборка похожих лотов |
| `LEFT` | Возврат на карточку товара | Встать в очередь снова |
| `DISCONNECTED` | Плашка «Переподключаемся…», данные не сбрасываются | Автоматический реконнект |

Три состояния (`EXPIRED`, `SOLD_OUT`, `DISCONNECTED`) — то, что жюри называет «серой зоной». Именно на них надо потратить время: у каждого есть текст-объяснение и явное действие.

### Защита от обхода очереди на фронте

`/checkout/:itemId` — защищённый роут: loader дёргает `GET /api/queue/entry?itemId=`, и если статус ≠ `GRANTED`, редиректит на страницу товара с тостом. Это UX-слой; настоящая проверка — транзакция в Postgres на бэке. В README надо явно написать, что фронтовый guard — удобство, а не механизм безопасности.

## 4. Контракт API (согласовать с бэкендом в первый час)

Авторизация в MVP — заголовок `X-User-Id` (регистрация вне скоупа кейса).

```
GET  /api/items                          → Item[]
GET  /api/items/:id                      → Item { id, title, price, images[], stock, sellerName, queueEnabled }
POST /api/queue/join      { itemId }     → QueueEntry
GET  /api/queue/entry?itemId=            → QueueEntry | 404
GET  /api/queue/:entryId/events          → SSE поток QueueEntry
POST /api/queue/:entryId/leave           → 204
POST /api/checkout        { entryId }    → Order { id, itemId, createdAt }
GET  /api/items/:id/similar              → Item[]        (AI-рекомендации)
GET  /api/queue/:entryId/eta             → { seconds, confidence }  (AI-прогноз)

QueueEntry {
  entryId, itemId, userId,
  status: 'QUEUED'|'GRANTED'|'EXPIRED'|'PURCHASED'|'SOLD_OUT'|'LEFT',
  position, totalAhead,
  grantedAt?, expiresAt?,     // ISO-8601, UTC — таймер считаем от разницы с сервером
  etaSeconds?
}
```

Ошибки — единый формат `{ code, message }`, коды: `ALREADY_IN_QUEUE`, `NO_ACTIVE_RIGHT`, `RIGHT_EXPIRED`, `ITEM_SOLD_OUT`, `NOT_FOUND`.

**Важно про таймер:** сервер отдаёт абсолютный `expiresAt`, а не «осталось N секунд». Один раз при загрузке считаем `serverTimeOffset` и рисуем таймер от него — иначе расхождение часов клиента ломает демо.

## 5. Структура проекта

```
frontend/
  src/
    app/          # провайдеры, роутер, глобальные стили, токены
    pages/        # CatalogPage, ItemPage, QueuePage, CheckoutPage, SuccessPage
    features/     # join-queue, queue-status, checkout, similar-items, user-switcher
    entities/     # item, queue-entry — типы, api, мелкие карточки
    shared/       # ui/, lib/ (useCountdown, useServerTime, useSSE), api/ (http-клиент)
    mocks/        # MSW handlers + сценарии
  .eslintrc / eslint.config.js, .prettierrc, .stylelintrc
  Dockerfile, nginx.conf
```

Feature-Sliced-lite: импорт разрешён строго вниз (`pages → features → entities → shared`), правило проверяется `eslint-plugin-boundaries`. Это ровно то «разделение по зонам ответственности», за которое жюри даёт баллы.

## 8. Риски

- **Демо на одном пользователе не докажет главного.** Переключатель пользователей — не украшение, а способ показать жюри защиту от двойной продажи. Делать обязательно.
- **Часы клиента.** Таймер только от `expiresAt` + серверный offset.
- **SSE через nginx.** Нужны `proxy_buffering off;` и `X-Accel-Buffering: no`, иначе события копятся в буфере. Проверить сразу на этапе 4, не в последний час.
- **Вкладка в фоне.** `setInterval` тротлится браузером — таймер пересчитывать от `Date.now()`, а не инкрементом.
- **Деплой откладывают на конец.** Поднять пустой контейнер на хосте уже на этапе 0.
