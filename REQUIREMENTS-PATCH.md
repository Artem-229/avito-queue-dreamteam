# REQUIREMENTS-PATCH.md

Дополнение к `docs/REQUIREMENTS.md` на вторую половину хакатона. Отдельный файл, а не правка
основного: так видно, что изменилось после разбора дефектов, и старые ID остаются валидными
для уже написанных тестов и PR. Нумерация — существующая.

> **Статус: реализовано**, с двумя уточнениями против текста ниже:
> * QUE-03 — тайбрейкер FIFO реализован по `(created_at, user_id)`, а не
>   `(created_at, id)`; ключ един для сортировки и вычисления позиции (INV-10).
> * RGT-08 — строже, чем в патче: `X-User-Id` не принимается вовсе, даже под
>   флагом. Идентификация только по подписанному токену (кука `session` или
>   `Authorization: Bearer`).
> Из INF-10 публичный деплой ещё не выполнен.

## Уточнения существующих требований

| ID | Было | Стало | Причина |
|---|---|---|---|
| **RGT-01** | Инвариант `granted + used <= total_stock` обеспечивается логикой `Reconcile` | Обеспечивается **констрейнтом** `catalog_items_stock_invariant` на уровне схемы; логика — первая линия, констрейнт — последняя | Логика без транзакции инвариант не держала (D-01). Констрейнт делает нарушение физически невозможным и становится главным ответом жюри |
| **RGT-02** | Длительность права настраивается | Колонка `catalog_items.hold_ttl_seconds`, дефолт 120 с, в сидах 90 с. Вычисляется в SQL | Было захардкожено 5 минут (D-07); 5 минут ещё и непроверяемо на защите |
| **RGT-07** | Гонка «оплата против истечения» закрыта атомарным `MarkAsUsed` | Без изменений, требование выполнено | Существующий `TestMarkAsUsed_Concurrency` корректен, оставить |
| **QUE-03** | FIFO по `created_at` | FIFO по `(created_at, id)` | Без тайбрейкера порядок недетерминирован (D-09) |
| **QUE-06** | Продвижение очереди синхронно, вызывается при входе в очередь | Вызывается **из любой операции**, читающей или меняющей состояние: статус, вход, чекаут, покупка, выход | Продвижение только из `Entry` означало, что слот не уходит следующему, если никто новый не встаёт в очередь (D-03) |
| **NFR-04** | Без фоновых воркеров | Без изменений; добавлено: перед блокировкой — дешёвая проверка `NeedsReconcile` без транзакции | Поллинг раз в секунду каждым ожидающим не должен брать блокировку впустую |

## Новые приёмочные сценарии

* **A-07 (D-03, ключевой).** Один товар, двое в очереди. Первый получает право и не покупает.
  **Никто новый в очередь не встаёт.** По истечении TTL второй при следующем опросе статуса
  получает право. Проверяется руками в двух браузерах и автотестом.
* **A-08 (D-02).** Право сгорело → `queue.status = expired` → повторный вход того же пользователя
  возвращает успех, а не `409 already in queue`.
* **A-09 (D-01).** 100 параллельных входов на товар в одну единицу → ровно одно активное право,
  `granted_count = 1`, ни одной ошибки констрейнта.
* **A-10 (RGT-01).** Прямая попытка записать `granted_count = total_stock + 1` в БД отклоняется
  констрейнтом. Доказывает, что защита лежит в схеме.
* **A-11 (RGT-08).** Подмена идентификатора пользователя в запросе не даёт доступа к чужому праву.
* **A-12 (QUE-08).** Выход из очереди освобождает слот следующему немедленно.
* **A-13 (D-05).** Два независимых контекста браузера против реального бэкенда: право получает
  только один. На моках этот сценарий выглядел бы пройденным ошибочно.

## Ограничения MVP — для README

Не реализовано сознательно: регистрация и авторизация, реальная оплата, полноценное оформление
заказа, списание стоков после оплаты (кейс объявляет их существующими). Заменено заглушками:
подписанная демо-сессия, `purchase_rights.status = used` как факт покупки, `total_stock`
не убывает — купленное считается через `used_count`.
